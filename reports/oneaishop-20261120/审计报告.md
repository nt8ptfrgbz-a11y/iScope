# 一人AI店 IPA Hook 风险审计

审计日期：2026-11-20。对象：用户提供的 `/Users/edy/Desktop/oneaishop_flutter.ipa`，应用 `com.tongchong.aishop`，版本 `2.1.201 (40)`。

**最需要优先检查的是 IM 签名材料进入客户端的设计。** 已从实际指令确认：客户端获取配置、解密其中两个字段，并把第二个解密字段作为 HMAC 密钥，在本地生成 UserSig。若该材料是生产 SDKAppID 的全局签名密钥，影响可能扩大到 IM 身份冒用。密钥权限范围和服务端是否接受跨身份签名，本次尚未验证。

本次同时确认了 Token 的普通首选项读写路径、可修改的本地课程用户判断、旧课程的课时上报链路，以及随 IPA 提供的精确业务符号。**尚未证明任意账号登录、免费获得付费课程、伪造真实支付成功或修改余额。**

## 范围与攻击前提

仅分析此 IPA 的配置、签名权限、资源、匹配 UUID 的符号和局部机器指令，没有读取应用源代码、运行或安装目标、修改 IPA、请求业务服务器、取得真实用户 Token，或生成攻击脚本。

大多数下列 Hook 面要求攻击者已经能够控制这个应用进程，例如在受控设备中运行可注入的副本。该包 `get-task-allow=false`，不能据此声称普通非越狱 iPhone 上的任意应用可以直接附加调试器。重新签名的副本也不会自动得到原应用的容器、Keychain 或原签名团队的服务权限。攻击者控制自己的客户端时，服务端仍须独立判定身份、支付和内容权限。

本应用业务逻辑主要位于 Flutter Dart AOT 的 `App.framework/App`。下文列出的 Dart 函数不是 Objective-C selector，不能直接按普通 Objective-C 方法替换方式处理。

## 1. IM 客户端签名：最高优先级核实

已确认调用链：

`CsRepository.getImCredential` → 响应模型 → 两次 `_decryptCredentialField` → `_generateUserSig` → `Hmac`。

第一项解密后被解析成正整数；第二项要求非空，并直接进入 HMAC 的密钥参数。解密使用 AES/CBC/PKCS7。包内同时有 `app-api/infra/appCs/configs/im-credential`、`sdkAppId`、`secretKey`、`TLS.identifier`、`TLS.sdkappid` 等字符串，但两个响应 JSON 键与这些字段名的对象池绑定尚未完整恢复。

关键静态位置（App 未加 ASLR 的 VA）：

- `loadLoginInfo`：`0x44d590`；`0x44d5cc` 获取配置；`0x44d688`、`0x44d6c4` 调用解密；`0x44d6ec` 调用签名。
- `_generateUserSig`：`0x44d7a8`；`0x44d90c` 编码解密材料；`0x44d92c` 构造 HMAC；`0x44d948` 计算 HMAC。
- `_decryptCredentialField`：`0x44de28`。

这意味着只保护传输或把配置加密后下发，仍无法阻止受控客户端观察其解密结果。若接口下发的是 IM 全局密钥，应作为严重问题处理。

**修复：** 由服务器根据已验证的当前用户身份签发短期 UserSig，客户端只接收该用户的成品凭证。全局密钥不得以可在客户端解密的形式下发。若确认已下发全局密钥，应停止分发并轮换，审查签发与 IM 登录记录。不能仅靠重命名、混淆或反 Hook 解决此问题。

## 2. Token：普通首选项存储已确认，真实泄漏尚未观察

当前 Flutter 代码的指令链为：

- 请求拦截器 `HeaderInterceptor.onRequest` 在 `0x5587b8` 调用 `SPHelper.getTokenInfo`。
- `getTokenInfo`（`0x41081c`）读取字符串，执行 `jsonDecode`，构造 `TokenEntity`。
- `SPHelper.getString` 经 `0x4cb08` 调用 `SharedPreferencesWithCache.getString`。
- `saveTokenInfo` 经 `0x580ac4` 调用 `saveString`，后者经 `0xdf5b0` 调用 `SharedPreferencesWithCache.setString`。

原生兼容路径另有直接证据：Runner 的 `AppDelegate.getTokenInfo()`（`0x100016838`）通过 `NSUserDefaults.standardUserDefaults` 读取 `UserTokenInfoMessage`、`UserOldTokenInfoMessage` 等值后序列化返回。

攻击者在已经控制的应用进程中，可从这些读写点或请求鉴权处截取当前会话。当前没有观察实际偏好文件、真实 Token 或日志输出；包内 `tokenJsonStr >>` 等日志字符串只能作为检查线索。普通首选项存储也不意味着其他普通 iOS 应用能够跨沙箱读取。

**修复：** 长期 Refresh Token 使用适当访问级别的 Keychain，清理迁移前的旧偏好数据；发布日志去除凭证；服务端使用短期 Access Token、刷新轮换、吊销与重用检测。Keychain 可以缩小落盘和备份泄漏面，无法阻止已控制进程观察正在使用的凭证。

## 3. 本地会员/课程状态可改，付费绕过未证实

`AppData.isSeriesCourseUser`（`0x630ad4`）读取本地用户资料，`UserInfo.isSeriesCourseUser`（`0x630b18`）根据一个字符串字段是否为空返回布尔值。这个本地结果可被受控客户端修改，能影响依赖它的展示或入口。

但修改这个布尔值不等于服务器给出未购课程。需要检查 `CourseApi.getCourseEntryUrl`、课程列表和实际播放凭据是否各自验证当前用户的购买权益；静态审计没有证明这些服务器校验缺失。

**修复：** 在服务端课程列表、H5/SSO 入口及媒体凭据接口分别检查课程归属；媒体签名短期有效，并按业务需要绑定用户/会话。本地会员标志仅用于界面体验。

## 4. 旧课程上报需要检查真实语义

已确认 `CourseVideoNotifier.selectPeriod` 在目标课时变化时，先调用 `OldRepository.finishPeriod` 并等待返回，然后调用 `_playVideo`。对应 `OldApi.finishPeriod` 构造一对键值的 Map，包含传入的课时整数参数，再发起 POST。包内存在 `api/course/finishPeriod` 字符串。

这给了受控客户端可操纵的上报边界。如果服务器凭这一次请求就将指定课时记为完成，可能出现虚假学习记录；但该接口也可能实际用于点击或开始学习，且旧接口是否仍用于生产未知。不能仅凭名字把它报成已经能“刷完课”。

**修复：** 核实接口业务含义，检查用户与课时归属、状态推进、重复上报和异常频率。若完课关联考试、证书或权益，不能直接信任客户端的完成标志或观看时长。

## 5. 网络配置与网页桥：配置风险确认，利用链待验证

`Info.plist` 确认 `NSAppTransportSecurity.NSAllowsArbitraryLoads=true`。App 同时内置公网 HTTP 基址、内网开发地址、测试/UAT 和生产 HTTPS 地址。因此可以确认发布材料中存在宽松配置，但不能据此断言生产登录或支付实际明文传输。

若敏感请求实际走 HTTP，通信路径上的攻击者可能直接读取或修改它，甚至无需 Hook。ATS 对不同网络栈的作用不同，Dart/Dio、WebView 和第三方 SDK 需要分别验证。出现 `badCertificateCallback` 或 `allowInvalidCertificates` 名称，不能证明业务代码真的信任任意证书。

WebView 和原生通道确实存在；同时也存在 `_isTrustedDocument`、`isTrustedCourseDocument` 的检查线索。没有证据证明任意网页能调用有权限的桥。应检查完整来源比较、导航/重定向、iframe 以及每个桥方法的参数与权限。

**修复：** 清理发布构建中的开发配置，缩小 ATS 例外，敏感通信全部走 HTTPS；隔离不同环境的凭证。网页桥逐项验证来源与权限；登录 Token 和支付状态由服务端核验。

## 6. 这一份 IPA 附带精确业务符号

`Symbols/0C7143A3-CBEB-C9ED-4C4F-F302E944EB58.symbols` 的 UUID 与 App AOT 二进制一致，可恢复 33,865 条地址、长度和名称记录，包括上述认证、IM、课程和订单函数。这显著降低攻击者定位 Hook 点的成本。

这是针对所提供 IPA 的确定事实。它不证明 App Store 最终下载的包也带同样的 `Symbols/`，也不授予注入权限。当前 `cryptid=0` 说明此分析样本未加密，不应单独当作 App Store 分发漏洞。

**修复：** 外发安装包去掉非安装必需的符号产物，把符号与调试信息保存在受控位置。混淆和完整性检测只能增加分析成本，不能替代服务器的授权检查。

## 建议按这个顺序验证和整改

1. **立即核对 IM 配置接口的响应字段和权限范围。** 确认是否把 SDKAppID 全局密钥交给客户端；若是，迁移到服务端签发并轮换密钥。
2. 在测试账号/测试环境检查：用户 A 能否取到用户 B 或未购买课程的真实播放凭据；忽略/篡改客户端登录、会员或支付状态后，服务端是否仍拒绝无效请求。
3. 核实 `finishPeriod` 的真实语义和服务端状态约束；区分打开课时、开始学习与完成课时。
4. 检查 Token 的落盘、备份、日志、退出登录失效与刷新重放；清理旧存储。
5. 记录生产实际网络目的地与证书拒绝行为，移除不必要的 HTTP/环境入口；移除外发符号。
